# CARE Binder — SAFEGUARDS (please read before editing `index.html`)

Hi, and thank you for taking care with this. 💙 A quick note on *why* this file exists:

**This app holds real clinical records for children in ABA therapy.** Lost data isn't an inconvenience here — it can mean a therapist's whole day of observations, or a supervisor's setup, gone. We have been through that several times, and it was painful. So the single most important thing in this project is: **never lose or overwrite data.** Features can wait; data safety cannot. Everything below exists to protect the people whose information lives in this app. When in doubt, choose the safer option and ask.

**Current version:** `v2026-11-22-CU`. Work on the `index.html` in this folder, and always **build on top of the current file** — never paste an older full copy over it, or you'll silently drop the protections below.

---

## Golden rules (in priority order)
1. **Protect the data first.** This is children's medical information. If a change touches saving, syncing, or any client record, treat it as high-risk: go slow, test it, and prefer "refuse and warn the user" over any chance of overwriting good data.
2. **Never fetch or query the Supabase client records directly** (children's PHI). If data needs checking or fixing, **write SQL for the user to run themselves** — never run it for them.
3. **Edit a copy, verify, then replace.** Write changes to a temp copy, run `node --check` on the extracted `<script>`, confirm it passes, *then* copy over `index.html`. Never write straight onto the only copy.
4. **Bump the version every release** (BUILD comment, `<title>`, `APP_VERSION`, new CHANGELOG entry) so devices can tell they're out of date.
5. **One editing chat/tool at a time.** Don't edit `index.html` while another chat or tool is editing it.
6. **The user commits `index.html` to GitHub** after any change they're happy with. GitHub is the backup and the recovery source — it has saved this project before.

## The data-safety architecture — do NOT break these (every one was a hard-won lesson)
All of a client's data — School Shadow setup AND records, school info, notes, comm notes — lives inside **one** client record. That makes concurrent edits dangerous, so every write must be careful.

- **Two, and only two, places may write a client record — and BOTH must go through the merge:**
  - **`sbSaveClient`** — re-reads the latest record, merges with `_mergeClientRow` (which uses `_mergeField` + `_ssIsEmptyish`, the *phantom-empty guard*), retries the read up to 3×, and **ABORTS with a "Save failed" message if it can't read** rather than risk an overwrite. Never revert it to a plain `sbUpsert('clients', clientToRow(c))`.
  - **`flushSave`** (the end-of-1:1-session background sync) — must route every changed client through `sbSaveClient`. It must **never** write a client with a bare `sbUpsert('clients', …)`. *(This was URGENT #3: flushSave bypassing the merge wiped the whole School Shadow setup. Fixed in v-AH. Do not undo it.)*
- **School Shadow merges piece by piece (v-BL):** in `_mergeClientRow`, `sup_notif._schoolShadow` goes through `_mergeSS` — daily `log`/`netLog` per day, `targets`/`net`/observation `notes` per item id, per-target notes `tnotes` per note id, everything else per key (`_ssM3` 3-way). A completely empty shadow copy never removes anything. Never revert to merging School Shadow as one block (a therapist's log and a supervisor's edit would overwrite each other). Unit tests: `/Users/songg./Claude/.claude/ssmerge_test.js` (16 scenarios).
- **Save baselines (v-BO):** `sbSaveClient` / `sbSaveLesson` / `sbSaveBIP` / `sbSaveABC` take a JSON snapshot of exactly what is sent BEFORE the network wait, and set `_recBaseline` to that snapshot ONLY if the server confirms (`sbUpsert` not null). Never re-stringify live objects after `await`, and never set the baseline on a failed save — otherwise an edit made during a save, or a failed save, is silently treated as saved and never retried.
- **Phantom-empty guard:** an empty or auto-created section may never overwrite real data on the server. Genuine edits and deletes still work. Lives in `_ssIsEmptyish` + `_mergeField`.
- **Free-text note drafts (so typing is never lost):** `_fdSkip / _fdKey / _restoreFieldDrafts / _clearFieldDraft` + the `input` listener; keep `_restoreFieldDrafts()` at the end of `render()`; keep the exclusions (`tx-sess-notes`, `ss-sess-notes`, `parent-note-input`, `sdnadd_*`); keep the `_clearFieldDraft(...)` calls in the note-add handlers. Drafts are **local only** — they never write to the database.
- **Note-draft clean-up (v-CL):** only free-text note drafts (`care_fd:*`) are cleared — after 3 days (`_fdSweep`, time stamps in `care_fd_ts`) and on a MANUAL logout (`_logoutClick` asks first; `doLogout(false)`). The automatic end-of-day sign-out calls `doLogout(true)` and must keep them. Session, BIP, School Shadow and stimuli drafts are unsaved data: never clear them automatically.
- **Admin staff changes (v-CP):** role, active and assigned cases are saved with PATCH of ONE column (`_asPatchUser`), the screen changes only after the database confirms, and case lists are merged with the latest server list first (`_acSave`) — never write a whole user row from a stale copy.
- **Logo (v-CQ):** the header, login screen and tab icon use `assets/care-logo.png` (same file as the Therapist Portal, referenced as `?v=1` — bump that number if the picture ever changes). The file must be deployed together with `index.html`; it is the only non-HTML file in the app. Do not put anything with client information in `assets/` (the repo is public).
- **Supervisor runs School Shadow as therapist (v-CR):** `_ssCanRecord()` is the ONE gate for recording School Shadow data (therapists; QCD when not view-only; supervisor/director only inside their own active as-therapist session on this case and only when the case is not view-only). `startSessionAsSup` allows own cases any day, another supervisor's case only on a cover day. `_ssCanSetup()` is false while `_coverSupLimited()` (setup/targets/timetable read-only on a case covered for another supervisor). Observation visits (School Observation notes, subject notes, recommendations) are unchanged.
- **Session banner (v-CS):** the four banner states (therapist / supervisor, not started / in progress) are built with the `sb` grid classes (`#sess-sticky.sb …`, one block set at the end of the main stylesheet). Keep `id="sess-sticky"` (print hides it), the element ids `ss-date`, `ss-time`, `ss-setting` (hidden select read by `startSessionFromBar`), `sv-date`, `sv-type`, and the function names in the buttons. Do not add more `#sess-sticky` rules to other media queries; adjust the `sb` block. While a supervisor acts as therapist, `_ssTxMode()` hides the School Shadow setup and the observation-note box.
- **Cover days (v-CN):** table `case_cover` (one row per cover day: client, person, date, read_from; ids are `cv-<client>-<person>-<date>` so a re-save merges instead of duplicating). Same `staff only` policy as every table. Loaded at start-up in `loadFromSupabase` as `DB.cover`, optional (missing table = no cover). `_coverMode(cid)` returns 'record' (cover day) / 'read' (read-ahead) / ''. Cover is wired into: client list filter, `selectClient`, `isViewOnly`, `_coverSupLimited` (a supervisor covering another's case gets a session but no program changes). Only the case supervisor / director / admin may add or remove cover (`_cvCanManage`). Cover removal goes through `_sbDel` (DB must confirm). This is app-side only until the database read lock (Stage 2).
- **School Shadow in-progress drafts:** `_ssSaveShadowDraft / _ssRestoreShadowDraft / _ssApplyCellValue / _ssClearShadowDraft`; keep `_ssRestoreShadowDraft()` at the end of `render()`, `_ssSaveShadowDraft()` in `_ssPick` and the `.ssn-c/.ssn-t` input listener, and the clear on discard.
- **Updates are a button, never a silent reload:** `#btn-update` + `_updateNavBtn` + `checkForUpdate`. Do not reintroduce auto-reload. Keep the 5-minute check.
- **Daily sign-out (privacy for a shared clinic device):** `_stampLoginDay`, `_checkDailyLogout`, the resume day-gate in `tryResumeSession`. Must stay gated by `_isBusy()` so it never interrupts someone mid-recording or mid-typing.
- **Every database request carries the logged-in person's token (`_sbAuth`)** — `sbFetch`, `sbUpsert` and `sbDeleteUser` all use it. Never go back to `'Authorization':'Bearer '+SUPABASE_KEY` for client data: once the database is locked to active staff (Row Level Security), requests with only the public key see nothing. Any new request helper must use `await _sbAuth()`.
- **Creating a login for someone else uses `_signUpNoSwitch`**, never `_supa.auth.signUp`, so the admin's own session is not swapped to the new account.
- **The database is locked to active staff (since 10 Oct 2026).** Every table has one policy, `staff only` (ALL to `authenticated`, checked by the `public.is_active_staff()` function: logged-in user whose `users.auth_id` matches and `active` is not false). Never re-add `allow all ... to public` policies. Any NEW table must get the same `staff only` policy, or it is either open to the world or invisible to the app. Songg has the undo saved in Supabase as `(keep) UNDO – Step 3 lock`.
- **Every SQL given to Songg starts with a name line** — `-- (keep) Name` or `-- (test) Name` — so saved queries in the Supabase SQL Editor can be labelled and cleaned up safely.
- **`lessons.phase_log` column (added for v-AS).** `lessonToRow` only sends `phase_log` when a lesson has entries. The column must exist in Supabase BEFORE any version that writes it goes live, or lesson saves with phase changes fail.
- **Anything saved during a visit/session is dated with `_workDate()`** (the visit/session date for this client, else today) — notes, mastered/hold/step/phase stamps, target notes. Never stamp those with plain `_todayLocal()` (v-BH fix: a back-dated visit split its notes across two days).
- **Visit type labels (v-BI):** anything saved during a visit/session also gets `kind:_workKind()` (or `masteredKind`/`heldKind`/`resumedKind`/`noteKind`/`introducedKind`) = 'clinic' / 'overlap' / 'school' / 'session'. The Day report filters supervisor updates by type (`KO()`); unlabelled and 'session' items always show; session data and behavior are whole-day. New dated stamps must add the matching kind. New lessons/SDs/targets record `addedDate`+`addedKind` (v-BJ) — any new creation path must too.
- **Dates use Thailand (device-local) time: always `_todayLocal()`**, never `new Date().toISOString().slice(0,10)` (UTC — saves before 07:00 got yesterday's date; fixed in v-AX).
- **Stimuli Checklist (v-AY): therapists never write the lesson.** Taps live in a LOCAL draft (`care_stim:<clientId>`) and are written into the session record at End & Save (`lessonData[].stim`), then the draft is cleared (also cleared on cancel). New stimuli live only in session records; the shared list = supervisor list (`t.stimuli`) + every stimulus used in past sessions. Only supervisors change the lesson (`t.stimOn`, `t.stimuli`, `t.stimHidden`). Keep `ld.stim` intact anywhere session lessonData is rebuilt. Renames are a supervisor map (`t.stimRename`) and "Export & clear" is `t.stimArchive` — old session records are never rewritten or deleted. Targets with `dataType:'stimuli'` must stay OFF the Session screen and Program Edit and out of saveSession / edit-session / no-data reminder / coverage bar (`_isStimT`, `_sdSess`, `_stimOnlyLesson`).
- **Per-client loading (v-BD).** Start-up loads only users/clients/lessons/BIPs (+ optional `client_session_summary` view). Sessions/behaviors/ABC load per client in `_ensureClientLoaded` (paged with `_sbFetchAll`, no row cap). The client screen must stay on the Loading/Retry screen until `_clientLoaded[cid]` is true; `saveSessionDraft` must not run before that; a failed page means NOT loaded (never use half-loaded data). Never re-add global `limit=` loads. Full Export must fetch everything (refuses partial).
- **BIP tab follows the session's setting (v-BR).** A BIP log is saved with the SESSION's setting (1:1 or School Shadow), so the graph on screen must be that setting too. Every session/visit start resets `_behViewCtx=null`; if someone taps the other setting during a session, the Log box is replaced by a "Switch to … to log" button (`_switchMsg`). Never show a Log box under a graph of a different setting — the entry would land on the other graph and look lost.
- **BIP rate needs real hours (v-BS).** Rate = count ÷ hours. A therapist session takes hours from the top bar (`ss-time`); a supervision visit has none, so the log form shows an "Hours watched" box (`bxhrs_<bipId>`, remembered as `bipHrs` in the visit state) and `logBIP` refuses to log a rate without it. Never fall back to 1 hour for a visit — that graphs the raw count as a rate.
- **The GitHub project is public.** Never commit client data, SQL with client details, or secret keys. Only the public `anon` key belongs in the code.
- **`_isBusy()`** is typing-aware (focused field, or typed in the last 90s, or an active session). Both auto-update and daily-logout rely on it. Keep it that way.

## Before deploying ANY change, sanity-check
- `node --check` passes on the extracted script, and `new Function(...)` constructs without error.
- These still exist in the file: `_mergeClientRow`, `_ssIsEmptyish`, `sbSaveClient`, the merge-routed `flushSave` (no bare `sbUpsert('clients'` outside `sbSaveClient`), `_restoreFieldDrafts`, `_ssRestoreShadowDraft`, `_updateNavBtn`, `_checkDailyLogout`.
- If you touched saving, syncing, drafts, update, or logout: **re-run the relevant logic test before shipping.**

## After a data-loss fix, remember the rollout
A code fix only protects a device **once that device is running the new version.** A device left open on an old cached version still runs the old, unsafe code. So after any save/sync fix: deploy to GitHub, then have **every** device fully close and reopen (not just refresh) and confirm the new version number, *before* re-entering any data.
